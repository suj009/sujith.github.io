Collapsing the handoff

The same intent gets re-typed three times between a product spec and a shipped screen. I built a pipeline that types it once — requirements into clickable layouts, approved layouts into production Flutter — and this is how it works, where it stops, and why the limits are the point.

The friction

In a retail brokerage, speed-to-market is most of the competition. New instruments, regulatory changes and competitor features all arrive on someone else's schedule, and the product that responds first tends to keep the customer.

The slow part is not the thinking. It's the relay.

A product owner writes a requirement. A designer reads it and redraws it on a vector canvas. A developer reads the canvas and rebuilds it in code. The same intent is expressed three times, in three languages, by three people — and each translation is a place where something quietly changes. Spacing drifts. A state gets missed. An edge case that was obvious in the spec never made it onto the artboard.

The cost isn't only the drift; it's the calendar. Weeks of review cycles go into re-agreeing things that were already agreed, and the front-end ends up carrying layout debt that nobody scheduled time to repay.

The bet

My bet was narrow and specific: the canvas is a translation step, not a thinking step.

Real design decisions — what the user is trying to do, what to show and what to hide, where the risk of an expensive mistake sits — happen before any pixel is placed. What happens on the canvas afterwards is mostly transcription: turning a decision into a layout, then turning that layout into something a developer can read.

If transcription is the bulk of the work, it's the part worth automating. Not the judgement. The typing.

Automate the transcription. Never the judgement.

The pipeline

Three stages, each with a human decision at the end of it.

Ingest
Spec → structure

Requirements are parsed into a structured layout intent: screens, hierarchy, states, and the data each element needs.

→
Align
Clickable low-fi

That structure becomes an interactive low-fidelity layout. Stakeholders click it, not imagine it — approval in a sitting rather than a sprint.

→
Compile
Flutter, web + mobile

The approved structure compiles to production-shaped Flutter for both platforms — the same layout, not two interpretations of it.

Ingest. The valuable output here isn't a picture, it's a structure — a machine-readable description of screens, hierarchy, states and data needs. Getting that structure explicit early is what surfaces the questions a spec left vague, and it surfaces them while they're still cheap to answer.

Align. Low fidelity is a deliberate choice, not a shortcut. A clickable grey layout invites argument about flow and hierarchy; a polished mockup invites argument about the shade of blue. I want the first conversation, and I want it before anyone has spent a week earning the right to be defensive about the work.

Compile. Once the structure is agreed, generating Flutter for web and mobile from that single source removes the interpretation gap between platforms. Engineering opens a pull request with clean layout code instead of a redlined PNG.

What it gave engineering

This is the part I'd defend hardest, because it's the part people assume is a threat.

The pipeline outputs layout. It doesn't output the things that make a trading app hard: state management, data contracts, live market streams, error and reconnection behaviour, the performance work that keeps a price grid smooth. Those are engineering problems, and they're where engineering time is actually worth spending.

So the effect wasn't fewer developers. It was developers spending less of the week rebuilding a layout somebody had already decided, and more of it on the systems only they can build. That's why the reception from the engineering side was good rather than defensive — the pipeline took the chore, not the craft.

The same argument, smaller

The order ticket in the Lab is one person designing and building a component in a single pass, in the browser. This pipeline is that instinct turned into infrastructure other people can use.

The guardrails

A tool that produces production code fast is a tool that produces mistakes fast. Three constraints keep it honest:

  • It generates structure, not decisions. Nothing in the pipeline chooses what to build or who it's for. Fed a bad requirement, it produces a fast, well-formed version of a bad idea — so the requirement is still the thing to argue about.
  • The design system is the ceiling, not the floor. Output is expected to conform to FDSG and still passes the same Design Review Board that hand-built work does. A shortcut around review would have made this a liability the first time it shipped something inconsistent.
  • Regulated surfaces stay slow on purpose. Order placement, funds movement and anything with a compliance obligation get the same scrutiny they always did. Speed is worth having on the eighty percent of screens where nobody's money is one tap away.

The honest limits

Three things it doesn't do, which I'd rather say here than in an interview.

It is weakest on novel interaction. When a screen has no precedent — the Options Scalper terminal is the obvious example — the pipeline has nothing to pattern-match against, and the work goes back to being hand-designed as it should be. It's strong on the well-understood eighty percent and no help at all on the interesting twenty.

The output is production-shaped, not production-final. Layout code lands clean; it still gets reviewed, wired and hardened like anything else. Anyone claiming an unattended path from spec to shipped feature is selling something.

And it requires someone who can read the code it writes. The reason I can run this is that I came into design from an engineering degree and have shipped front-end myself. Handing this to a designer who can't evaluate the output would replace a slow relay with a fast one that nobody can audit — which is exactly the problem to solve as it scales.

From pilot to framework

I built and ran this as an individual pilot first, on real features with real deadlines, because a demo proves nothing and a shipped feature proves everything. The delivery speed is what got it noticed by leadership, and the mandate that followed was to turn a personal workflow into something the organization can use.

That's the current work, and it's a different problem from building the thing. A tool one person can drive is not a framework — a framework needs defaults that fail safely, output other squads can trust without reading every line, and a review path that catches what the pipeline gets wrong. Making it institutional means making it boring, which is the part I'm building now.

The outcome

spec → code one pipeline in place of a three-step relay, with the intent typed once instead of three times.
↓ drift layout debt removed at the source — the approved layout is the build input, not a reference for a rebuild.
web + mobile both platforms compiled from one structure, so they stop diverging by interpretation.
eng focus developer time moved off layout rebuilds and onto state, data contracts and live market streams.
pilot → org recognised by leadership on delivered work; now being scaled into a framework other squads can use.

On the numbers Cycle-time figures, internal specs and the pipeline's implementation details are covered by broker-dealer confidentiality and stay off a public page. Everything here is framed in terms I can stand behind publicly; a full walkthrough is available under NDA during an interview process.

The interesting claim here isn't that AI can generate a screen — plenty of things generate screens. It's that a designer who understands both the product and the code can own the whole path, and that the handoff was never a law of nature. It was just the place we'd agreed to stop.
